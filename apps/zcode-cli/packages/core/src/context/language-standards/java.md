# Java 编码规范

> 适用于 Java 工程(后端、Android、服务端)。用户需求模糊时,先按本规范澄清边界,再实现。

## 1. 风格与命名

- 类/接口/枚举用 PascalCase,方法/变量用 camelCase,常量用 UPPER_SNAKE_CASE,包名全小写。
- 缩进以仓库格式化配置为准;中文注释,代码保留英文标识符。
- 接口命名尽量以 `I` 或以行为命名;避免无意义缩写。

## 2. 类型与空值

- 尽量用不可变类型与 `final`;字段 `final`、方法参数尽量不可变,减少副作用范围。
- 空值管理:优先 `java.util.Optional` 表达可缺省,但不要在可空返回值上滥用;明确区分缺省与 null 语义。
- 使用类型化集合(泛型),不要用 `raw type`;不使用受检异常之外的隐式空引用传播。
- 数据契约(跨进程/网络)用明确的 schema/record 表达并做边界校验,而非仅靠对象。

## 3. 可变性、并发与线程安全

- 共享可变状态限定在唯一 owner;优先用 `java.util.concurrent` 而非裸 `synchronized` 裸锁。
- 明确并发形态:不可变对象 / 线程限制 / 无锁结构/乐观并发,选择最能表达意图的一种,不混用。
- 禁止在可变静态字段上散落状态;`static` 真正用于不变量与常量。
- 竞态与取消语义,优先使用 `CompletableFuture` 与明确超时,不用 sleep 掩盖同步。

## 4. 错误与异常

- 异常按场景分级:受检异常用于可恢复、调用方可处理的;`IllegalArgumentException` 等运行时异常用于编程错误;用自定义业务异常带结构化字段区分失败原因。
- 不吞异常;捕获后能恢复才捕获,否则向上冒泡,保留 cause。
- `try-with-resources` 关闭资源;不要在 `finally` 里覆盖主异常。

## 5. 结构与架构

- 单文件 ≤ 400 行;按包与责任拆分;避免超大类(上帝对象)。
- 业务逻辑与 I/O(网络/DB/文件/外部服务)分离,收敛到 repository/adapter;依赖注入优于静态单例。
- 对外接口用小接口契约,避免循环依赖与内部实现深挖。

## 6. 构建 / 测试 / 工具

- 以仓库工具(Maven/Gradle)为准;行为变更先补测试(JUnit 之类的列式等)。
- 避免引入未使用依赖;第三方代码确认许可证与来源。

## 7. 常见陷阱

- 受检异常与流式 API 组合困难;`Optional` 链式误用导致难以调试。
- 字符串拼接用 StringBuilder/模板;`equals`/`hashCode` 与 `==` 语义混用。
- 集合 `ConcurrentModificationException`、日期时区与正负数精度陷阱。
