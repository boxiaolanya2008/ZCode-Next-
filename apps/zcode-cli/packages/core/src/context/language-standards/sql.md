# SQL 编写规范

> 适用于 SQL(关系数据库查询/迁移)。用户需求模糊时,先按本规范明确目标 DBMS 与结果预期,再写查询。

## 1. 命名与惯例

- 表/列用 snake_case;主键/外键命名明确(`id`、`<table>_id`);索引名带可读前缀。
- 关键字大写、标识符小写,语句缩进一致;不写超过一屏难读的长单行。
- 表别名语义化并全查询一致;避免无意义的单字母别名(除非极短且清楚)。

## 2. 正确性与类型

- 用参数占位符/绑定参数,不要把输入拼进 SQL 字符串(防注入)。
- 明确类型转换与比较语义;避免依赖 DBMS 隐式转换与字符串日期比较。
- 处理 `NULL`:用 `IS NULL`/`IS NOT NULL`,明确三元逻辑;聚合 `COUNT(col)` vs `COUNT(*)` 语义不同。

## 3. 查询与性能

- 只取需要的列与 `WHERE` 充分过滤;`SELECT *` 仅用于确实全选。
- 连接用显式 `JOIN` 语义并利用索引;**避免无谓的子查询/游标**,能用索引/`EXISTS` 就优先。
- 大数据集注意 `LIMIT`;避免在 `WHERE` 中调用无法索引的表达式。
- 排序、去重与聚合(`GROUP BY`/`HAVING`)语义明确;窗口函数按需使用。

## 4. 事务与一致性

- 语句组需要原子性时用事务,并明确隔离级别;迁移脚本保持可回滚。
- 数据迁移先备份/加校验;避免长锁与大批量多次往返。

## 5. 可维护 / 安全

- 敏感数据不要暴露在注释/日志/示例;权限最小化。
- 查询与 schema 变更随仓库迁移脚本进行,不做临时手工改动。

## 6. 常见陷阱

- `NULL` 与 `=`/`!=` 的语义;字符串与数字比较隐式转换;`OR` 无法利用索引导致扫全表。
- 时区与 `timestamp` 比较;`LIKE` 通配转义。
